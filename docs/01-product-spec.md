# 사주풀이 로또번호 추첨기 — 제품 기획서

> 문서 버전: v0.1 (MVP 기획) · 작성: PM/기획 · 작성일: 2026-09-03
> 상태: 초안 (개발 리드 인수인계용)

---

## 1. 한 줄 소개 & 비전

**한 줄 소개**
> "당신의 사주에 담긴 오행의 기운으로 오늘의 행운 번호를 뽑아드립니다."

생년월일시(사주)를 입력하면 명리학 요소를 로또 6/45 번호로 변환해 "나만의 행운 번호"와 짧은 사주 풀이를 제공하는 엔터테인먼트 웹 서비스.

**비전**
- 로또를 "확률 게임"이 아닌 "이야기가 있는 재미"로 재해석한다.
- 매주 로또 구매라는 반복 행동에 "내 사주 기반"이라는 개인화된 서사를 얹어, 뽑는 순간 자체를 콘텐츠로 만든다.
- 장기적으로는 사주·타로·별자리 등 "운세 기반 개인화 추첨/추천" 놀이터로 확장.

---

## 2. 문제 정의 / 동기

**관찰된 상황**
- 사람들은 로또 번호를 "그냥 자동"으로 뽑기엔 심심해하고, "수동"으로 뽑자니 근거가 없어 고민한다.
- 생일, 기념일, 꿈 해몽 등 "의미 있는 숫자"로 번호를 정하는 문화가 이미 널리 존재한다 (자발적 서사 부여).
- 사주/운세 콘텐츠는 한국에서 꾸준한 수요가 있는 오락 카테고리다.

**문제**
- 번호를 고를 "그럴듯한 근거"와 "재미있는 스토리"가 결합된 서비스가 마땅치 않다.
- 기존 "행운번호 생성기"는 단순 난수 + 별 의미 없는 문구라 재방문·공유 동기가 약하다.

**동기 (왜 사주 + 로또인가)**
- **개인화**: 생년월일시는 사람마다 다르므로 "나만의 번호"라는 소유감이 생긴다.
- **서사성**: 오행/십성 풀이가 붙으면 "왜 이 번호인지" 설명이 되어 공유·대화 소재가 된다.
- **결정성 + 우연성의 균형**: 같은 사주는 (규칙에 따라) 재현 가능하게 만들 수도 있고, 매주 변주를 줄 수도 있어 재방문 설계가 유연하다.

## 3. 타겟 사용자 (페르소나)

### 페르소나 A — "재미로 사보는 로또러" 김운수 (34세, 직장인)
- 매주 1~2회 편의점에서 로또를 산다. 당첨보다 "기대하는 즐거움"이 목적.
- 번호는 매번 자동/수동을 섞는데, 수동으로 고를 때 근거가 없어 아쉽다.
- 운세 앱을 종종 본다. "오늘의 운세" 정도는 습관적으로 확인.
- **니즈**: 뽑는 재미 + 이야깃거리. 결과를 카톡으로 친구에게 보내고 싶다.

### 페르소나 B — "운세 좋아하는 콘텐츠 소비자" 이사주 (27세, 대학원생/직장인)
- 사주·타로·MBTI 등 자기 서사형 콘텐츠를 즐기고 SNS에 공유.
- 로또는 가끔 재미로만. 당첨 목적보다 "결과 화면이 예쁘고 그럴듯한지"가 중요.
- **니즈**: 그럴듯한 사주 풀이 텍스트 + 캡처해서 공유하기 좋은 결과 화면.

## 4. 핵심 가치 제안

| 가치 | 설명 |
|---|---|
| **나만의 번호** | 내 사주에서 나온 번호라는 개인화된 소유감 |
| **이야기가 있는 추첨** | 번호마다 "왜 이 번호인지" 오행·십성 기반 풀이 제공 |
| **부담 없는 재미** | 무료·비회원·즉시 결과, 당첨 보장 아님을 명확히 한 순수 엔터테인먼트 |
| **공유 가능성** | 캡처/공유하기 좋은 결과 화면으로 자연 확산 |

**한 문장 포지셔닝**
> "심심한 자동번호 대신, 내 사주로 뽑은 이야기 있는 행운 번호."

## 5. MVP 핵심 기능 vs 백로그

### MVP 핵심 기능 (반드시 v1에 포함)

1. **사주 입력**
   - 입력: 생년월일(양력/음력 선택), 태어난 시(모름 옵션 포함), 성별(선택).
   - 최소 입력으로도 결과가 나오게 (시 모름 → 시주 제외 규칙 적용).
   - 유효성 검사(미래 날짜 방지, 존재하지 않는 날짜 방지).

2. **명리 요소 → 번호 변환 (기획 규칙)**
   - 입력을 천간·지지·오행 정보로 환산 (변환 규칙은 부록 참조).
   - 오행 분포/가중치를 1~45 번호대에 매핑하여 6개 번호 도출.
   - 중복 없는 6개 보장 로직.

3. **결과 화면**
   - 추첨된 6개 번호 (로또 공 스타일 시각화, 번호대 색상 반영 권장).
   - 짧은 사주 풀이 텍스트 (2~4문장): 강한 오행, 부족한 오행, 그에 따른 번호 선택 이유.
   - **면책 문구** 상시 노출 ("본 결과는 재미를 위한 것이며 당첨을 보장하지 않습니다").

4. **재추첨 (다시 뽑기)**
   - 같은 사주 기반이되 "변주 시드"를 더해 다른 조합 제시 (하루 N회 제한은 백로그).

5. **결과 공유 기본 동작**
   - 최소한 결과 화면 캡처가 깔끔하게 되도록 레이아웃 정리 (전용 이미지 생성은 백로그).

### 백로그 (나중에)

- 하루 추첨 횟수 제한 / "오늘의 번호" 데일리 고정 모드
- 결과 이미지 카드 자동 생성 + SNS/카톡 공유 버튼
- 지난 추첨 기록 저장 (로그인/로컬 저장)
- 실제 회차 당첨번호 대조 & "맞춘 개수" 재미 피드백
- 십성(비겁·식상·재성·관성·인성) 기반 상세 풀이 고도화
- 궁합 번호(두 사람 사주 조합), 커플/가족 모드
- 다국어(영어), 유료 프리미엄 상세 풀이
- 로또 외 연금복권/기타 추첨 지원

## 6. 사용자 플로우

```
[랜딩]
  └─ "행운 번호 뽑기" CTA
       │
       ▼
[사주 입력]
  ├─ 생년월일 (양/음력 토글)
  ├─ 태어난 시 (선택: 모름 가능)
  ├─ 성별 (선택)
  └─ [번호 뽑기] 클릭
       │
       ▼
[처리]  (짧은 로딩/연출 애니메이션 - "기운을 읽는 중...")
  ├─ 입력 → 천간·지지·오행 환산
  ├─ 오행 가중치 계산
  └─ 1~45 매핑 → 6개 번호 확정
       │
       ▼
[결과 화면]
  ├─ 행운 번호 6개 (공 시각화)
  ├─ 사주 풀이 텍스트 (강/약 오행 + 선택 이유)
  ├─ 면책 문구
  └─ [다시 뽑기] / [처음으로]
```

**핵심 UX 원칙**
- 입력은 3필드 이내, 30초 안에 결과 도달.
- 처리 연출은 짧게(1~2초) — 기대감은 주되 지루하지 않게.
- 결과는 한 화면에 다 보이게 (스크롤 최소화, 캡처 친화적).

## 7. 성공 지표 (토이 규모 현실 지표)

토이프로젝트인 만큼 "매출/DAU 만명" 같은 지표 대신 **작동·재미·재방문**에 집중.

**1차 (동작 확인)**
- 입력→결과까지 에러 없이 완주하는 세션 비율 ≥ 90%
- 평균 결과 도달 시간 ≤ 30초

**2차 (재미/참여)**
- 세션당 평균 "다시 뽑기" 횟수 (목표: ≥ 1.5회 → 재미 신호)
- 결과 화면 체류 시간 (풀이를 읽는지)
- 재방문율 (일주일 내 재접속 비율, 목표: 소소하게 ≥ 15%)

**3차 (확산, 백로그 기능 도입 후)**
- 공유 버튼 클릭 수 / 공유 후 유입
- 지인 추천을 통한 신규 유입

> 지표 수집은 최소한의 익명 이벤트 로깅(페이지뷰, 뽑기 클릭, 다시뽑기 클릭)만으로 시작. 생년월일 등 민감정보는 지표 로깅에 포함하지 않는다(8장 참조).

## 8. 제약 / 리스크

### 8-1. 사행성 / 도박 윤리
- **리스크**: 로또(복권)와 연관된 서비스는 사행심 조장 오해 소지가 있음.
- **완화**:
  - 실제 복권 구매/결제/판매와 **무관**함을 명시. 번호 "제안"만 하고 판매하지 않음.
  - "당첨 보장 없음, 순수 오락" 면책 문구 상시 노출.
  - 과몰입 유도 문구(예: "이번엔 무조건 1등!") 사용 금지.
  - 미성년자 대상 아님을 안내 (필요 시 연령 고지).

### 8-2. 면책 / 법적 고지 (필수 카피 예시)
- "본 서비스가 제공하는 번호는 명리학적 요소를 활용한 **엔터테인먼트 콘텐츠**이며, 로또 당첨을 보장하지 않습니다."
- "본 서비스는 복권을 판매하거나 구매를 대행하지 않습니다."
- "사주 풀이는 재미를 위한 해석이며, 어떤 결정의 근거로 삼지 마십시오."

### 8-3. 개인정보 (생년월일시) 취급
- **리스크**: 생년월일시 + 성별은 개인 식별성이 있는 민감 정보로 다뤄질 수 있음.
- **원칙 (Privacy by Design)**:
  - **저장하지 않는다**: MVP는 입력값을 서버 DB에 저장하지 않고, 계산 후 폐기(가능하면 클라이언트 측 계산).
  - **로깅 금지**: 분석/에러 로그에 생년월일시 원문을 남기지 않는다.
  - **회원가입 없음**: MVP는 비회원. 기록 저장 기능(백로그) 도입 시 별도 동의·최소 수집 원칙 적용.
  - **개인정보 처리방침**: 저장을 안 하더라도 "입력값을 저장하지 않으며 결과 계산에만 사용한다"는 안내 페이지 제공.

### 8-4. 명리학 정확성 / 신뢰성 리스크
- **리스크**: "사주 풀이"의 정확성에 대한 기대와 실제 규칙(단순 매핑) 간 괴리.
- **완화**: 처음부터 "정통 명리 상담이 아닌 재미용 해석"임을 톤앤매너로 명확히. 단, 오행 산출 로직은 최대한 그럴듯하게(실제 만세력 기반) 구현해 신뢰감은 확보.

### 8-5. 기술적 제약
- **음력↔양력 변환, 절기(입춘) 기준 연주(年柱) 처리, 시주(時柱) 계산**은 명리 계산의 정확도 핵심이자 난이도 높은 부분. MVP에서 어디까지 정확히 할지 개발 리드가 범위 결정 필요 (부록의 규칙은 "그럴듯함" 우선).

## 10. 부록: 번호 변환 규칙 구체 예시 (개발 인수인계용)

> 목적: 개발 리드가 로직을 구현할 때 참고할 **기획 관점의 규칙 아이디어**. 실제 알고리즘/자료구조/스택은 개발 단계에서 확정.
> 공통 전제:
> - 결과는 항상 **1~45 범위, 중복 없는 정수 6개**.
> - 오행(五行) 5요소: **목(木)·화(火)·토(土)·금(金)·수(水)**.
> - 번호대 기본 매핑(제안): **목 1~9 / 화 10~18 / 토 19~27 / 금 28~36 / 수 37~45** (각 오행당 9개 구간).

### 규칙 A — "오행 가중치 배분" 방식 (직관적, 설명하기 쉬움)

**아이디어**: 사주 8글자(연·월·일·시의 천간·지지)에서 각 오행이 몇 개인지 세고, 강한 오행의 번호대에서 더 많이 뽑는다.

**절차**
1. 사주팔자에서 오행 개수를 집계한다. 예: 목2, 화1, 토3, 금0, 수2 (합계 8. 시 모름이면 6글자 기준).
2. 각 오행에 배정할 "뽑을 개수"를 계산한다. 총 6개를 오행 비중대로 배분하되, 규칙 보정:
   - 기본 배분 = round(6 × 해당오행수 / 전체글자수).
   - **부족(0개) 오행 보정**: 개수 0인 오행이 있으면 "부족한 기운을 채운다"는 명리 논리로 **최소 1개**를 그 오행 번호대에서 강제 배정(재미 요소 + 설명 논리).
   - 배분 합이 6을 넘거나 모자라면 가장 강한 오행부터 ±1 조정하여 정확히 6으로 맞춘다.
   - 예(목2/화1/토3/금0/수2): 토2, 목1, 수1, 금1(보정), 화1 → 합 6.
3. 각 오행 번호대(9개 구간) 안에서 실제 번호를 고른다.
   - 구간 내 선택은 시드 기반 결정적 난수(아래 "시드" 설명) 사용 → 같은 입력이면 같은 결과(재현성).
   - 같은 번호대에서 여러 개 뽑을 땐 중복 없이.
4. 최종 6개가 모이면 오름차순 정렬 후 반환.

**결과 풀이 텍스트 생성 예**
> "당신의 사주는 토(土) 기운이 강해 안정과 중심을 상징합니다(19~27번대에서 2개 선택). 반면 금(金) 기운이 부족해 이를 보완하는 번호(28~36번대) 1개를 더했습니다. 나머지는 목·화·수의 균형을 반영했습니다."

### 규칙 B — "천간·지지 시드 결정적 추첨" 방식 (재현성·구현 단순)

**아이디어**: 사주 정보를 하나의 **정수 시드**로 압축하고, 그 시드로 결정적(deterministic) 추첨을 돌린다. "같은 사주 = 같은 운명의 번호"라는 서사와 잘 맞고 구현이 단순.

**절차**
1. 사주 구성요소에 고정 코드값을 부여한다.
   - 천간(10개) 갑~계 → 0~9, 지지(12개) 자~해 → 0~11 등 사전 정의 테이블.
   - 예: 시드 문자열 = `연간·연지·월간·월지·일간·일지·시간·시지` 코드를 이어붙임 (시 모름이면 시 부분 생략 또는 고정값).
2. 시드 문자열을 하나의 정수로 변환한다 (예: 각 코드에 자리 가중치를 곱해 합산, 또는 해시 함수 적용).
3. 이 시드로 **결정적 셔플/추첨**을 수행한다.
   - 1~45 배열을 시드 기반 난수로 섞은 뒤 앞에서 6개를 취하는 방식 (Fisher–Yates류를 시드 고정으로).
   - 결과: 같은 사주 → 항상 같은 6개 (재현성 보장).
4. "다시 뽑기"는 시드에 **변주값**을 더한다.
   - 예: 시드 + (오늘 날짜 정수) 또는 시드 + (다시뽑기 카운트) → 매번 다른 결과지만 여전히 그 사주에서 파생된 번호라는 설명 유지.
5. 오름차순 정렬 후 반환.

**결과 풀이 텍스트 생성 예**
> "당신의 일간(日干)은 '갑(甲)'으로 큰 나무의 기운입니다. 이 타고난 기운을 시드로 삼아 운명의 6개 번호를 배열했습니다. 오늘의 변주가 더해져 어제와는 다른 조합이 나타났습니다."

### 두 규칙 비교 (개발 선택 가이드)

| 항목 | 규칙 A (가중치 배분) | 규칙 B (시드 결정적) |
|---|---|---|
| 설명 서사 | 오행 강약이 번호에 직접 반영돼 풀이가 풍부 | "같은 사주=같은 번호" 운명론적 서사 |
| 구현 난이도 | 중 (배분·보정 로직 필요) | 하 (시드 → 셔플) |
| 재현성 | 시드 고정 시 재현 가능 | 기본 재현성 강함 |
| 재추첨 변주 | 배분은 유지, 구간 내 재선택 | 시드 변주값으로 처리 |
| 추천 | 풀이 콘텐츠 강조하고 싶을 때 | 빠른 MVP·운명론 톤 강조할 때 |

> **MVP 권장**: 규칙 B(시드)로 뼈대를 먼저 만들어 빠르게 동작시키고, 풀이 텍스트 품질을 위해 규칙 A의 오행 집계/보정 로직을 결과 풀이 생성에 접목하는 **하이브리드**도 고려. (번호 선택은 B, 풀이 설명은 A의 오행 강약 데이터 활용.)
